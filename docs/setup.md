# ローカルセットアップ・既存V4の更新

[READMEへ戻る](../README.md) · [操作ガイド](usage.md) · [セキュリティ・テスト](security-and-testing.md) · [設計書](../system_design.md)

この手順は、Ver.4を自分のPCで動かすためのものです。[GitHubのソースコード](https://github.com/ZUPPY-0727/shift_management_ver4)は公開していますが、Webアプリはインターネットへ公開・デプロイしていません。クラウド配備やPostgreSQLへの移行の手順ではありません。

既にV4のDBを使っている場合は、DBを削除せず、[既存V4の更新](#4-既存v4のdb更新)へ進んでください。初回準備のやり直しや管理者の再作成は不要です。

以下のコマンドは利用者が実行する手順です。このドキュメント整備では、インストール・起動・DB操作・テストを実行していません。テスト方法と確認状況の扱いは[セキュリティ・テスト](security-and-testing.md)を参照してください。

## 1. 必要な環境とソースの取得

- Python 3.10以降
- PowerShellまたはAnaconda PowerShell Prompt
- ローカルブラウザ

まだソースを取得していない場合は、例えば次のように公開リポジトリを取得します。`C:\projects`は配置先の例なので、実在する作業用フォルダに読み替えてください。既存のV4フォルダに上書きするためのコマンドではありません。

```powershell
cd C:\projects
git clone https://github.com/ZUPPY-0727/shift_management_ver4.git
cd shift_management_ver4
```

既にダウンロード・配置済みの場合は、そのVer.4フォルダへ移動します。

```powershell
cd C:\projects\shift_management_ver4
```

以降は、`app.py`と`requirements.txt`が直下にあるVer.4フォルダで実行します。親ワークスペースやV3フォルダと間違えないでください。

V1・V2・V3のソースやDBは変更せず、V4とは分離して扱います。V1～V3からのデータ移行は行いません。旧バージョンのDBをV4へコピーしたり、初期化対象に指定したりしないでください。

## 2. 初回準備（新規環境のみ）

### 2.1 Python環境と依存関係

既にAnacondaなどの専用Python環境がある場合は、その環境を有効にして使用してください。新しいPCでは、任意で仮想環境を作成できます。

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

PowerShellの設定で有効化できない場合は、既存のAnaconda環境を使うか、以降の`python`を`.\.venv\Scripts\python.exe`に読み替えてください。PowerShellのセキュリティ設定を変更する必要はありません。

使用するPython環境に依存関係をインストールします。

```powershell
python -m pip install -r requirements.txt
```

`pip install -r requirements.txt`でもインストールできますが、`python -m pip`なら選択中のPython環境を明示できます。

[requirements.txt](../requirements.txt)には、Flask（`>=3.1,<4`）、直接importするWerkzeug・Click、自動テスト用pytest（`>=8,<10`）を記載しています。Werkzeug・ClickはFlaskの依存にも含まれ、個別のバージョン指定はありません。SQLite、secrets、pathlibなどはPython標準ライブラリなので追加インストールは不要です。未使用のPostgreSQLドライバーなども含めていません。

このファイルは依存関係を完全固定したロックファイルではありません。別PCへの移動や将来の依存更新時には、導入されたバージョンを確認し、テストを再実行してください。

### 2.2 セッション用の秘密鍵

固定の開発用キーはありません。同じPowerShellで、32文字以上の安全な秘密値を環境変数`SHIFT_MANAGEMENT_V4_SECRET_KEY`に設定します。次のコマンドは、ランダム生成した値を画面へ表示せず環境変数に代入します。

```powershell
$env:SHIFT_MANAGEMENT_V4_SECRET_KEY = python -c "import secrets; print(secrets.token_hex(32))"
```

これはPowerShell用の書き方です。コマンドプロンプトの`set "変数=値"`とは異なります。仮想環境を有効化せずに使う場合は、このコマンド内の`python`も`.\.venv\Scripts\python.exe`に読み替えます。

生成した秘密値をREADME、ソース、GitHub、スクリーンショットへ貼り付けないでください。本アプリは`.env`の自動読み込みを前提としていません。

この設定は現在のPowerShellに対して有効です。新しいPowerShellでは再設定が必要です。キーを変えると既存のログインセッションは無効になり、再ログインが必要です。継続して同じログインセッションを使う場合は、適切な秘密情報管理の方法で同じ安全なキーを設定します。

### 2.3 新しいV4データベース

新規環境だけで実行します。既存V4の更新には[第4節](#4-既存v4のdb更新)の`migrate-db`を使用してください。

```powershell
python -m flask --app app:create_app init-db
```

`instance/shift_management_v4.db`にV4のテーブル、店舗基本時給1,280円、店舗共通の休憩ルールを作成します。管理者・従業員・シフトのデモデータは自動登録しません。通常起動時に、未初期化DBを自動作成することもありません。

現行構造への`init-db`の再実行でも、既存の業務データや変更済みの設定は消しません。ただし、毎回実行する必要はありません。旧構造のV4は初期化を拒否して`migrate-db`を案内し、V4以外の構造や不完全なDBも誤上書きを避けるためエラーにします。エラー対処としてDBを削除しないでください。

### 2.4 自分用の管理者を作成

```powershell
python -m flask --app app:create_app create-admin --username manager
```

`manager`は例です。自分が使用する管理者名に変更できます。ユーザー名は前後の空白を除いて1～100文字で、登録済みの名前は重複作成できません。管理者パスワードと確認用パスワードを非表示で入力します。

パスワードは8～64文字で、ASCII英字と半角数字を各1文字以上含めます。V3で公開したデモ用パスワード系統は管理者作成時に拒否します。新しいパスワードを設定してください。

固定の管理者ID・パスワードはありません。以後は、自分で作成したユーザー名とパスワードでログインします。管理者登録画面とデモ従業員作成CLIはありません。従業員は管理者画面で登録します。登録・仮パスワード・本人変更の流れは[操作ガイド](usage.md)を参照してください。

必要な場合は環境変数`SHIFT_MANAGEMENT_V4_ADMIN_PASSWORD`からも管理者パスワードを渡せますが、通常は非表示入力を推奨します。環境変数を使用した後は、現在のPowerShellから解除してください。

```powershell
Remove-Item Env:SHIFT_MANAGEMENT_V4_ADMIN_PASSWORD
```

### 2.5 ローカル起動

```powershell
python app.py
```

ブラウザで次のURLを開きます。

```text
http://127.0.0.1:5000
```

起動先は`127.0.0.1`、ポートは`5000`で、debugは無効です。終了するときは起動中のPowerShellで`Ctrl+C`を押します。これはローカル確認用のFlask開発サーバーであり、インターネット公開用の構成ではありません。

## 3. 2回目以降の起動

Ver.4フォルダへ移動し、使用するPython環境と秘密鍵を同じPowerShellで準備して起動します。

```powershell
python app.py
```

既存DBがある場合、`init-db`や`create-admin`を毎回実行する必要はありません。新しいPowerShellで秘密鍵を生成し直す場合は、ログインし直してください。コード更新でDB構造の更新を求められた場合だけ、次節の手順を行います。

## 4. 既存V4のDB更新

既存DBを削除したり、初回準備をやり直したりしないでください。今回の内部DB構造はschema 6ですが、製品名はVer.4のままです。更新対象はV4のschema 4または5で、V1～V3のDBを移行するコマンドではありません。

1. アプリを`Ctrl+C`で停止します。
2. いつものPython環境と秘密鍵を準備した、同じPowerShellで次を実行します。

```powershell
python -m flask --app app:create_app migrate-db
```

schema 5→6では、確定済み勤務の追加・編集・削除を一律に拒否していたトリガーを置き換えます。確定勤務の休憩記録を必須にする制約、勤務月の一致・固定、確定状態と初回確定日時の保持は維持します。業務テーブルの削除・再作成、新しい履歴テーブル、アカウント・シフトの初期化、保存済み休憩の一括再計算は行いません。

schema 4からの場合は、先に認証版`auth_version`、変更必須フラグ`must_change_password`、ID固定トリガー、一回限りの発行操作を管理する`one_time_tokens`も追加してからschema 6へ進みます。全段階を一回のバックアップ・トランザクションで扱います。schema 5からの更新では既存の認証情報を変更しません。

更新前に`instance/backups/before_employee_accounts_*.db`へ自動バックアップを保存し、整合性を確認します（ファイル名の接頭辞は従来と共通です）。保存・確認に失敗した場合は構造更新を中止し、更新途中に失敗した場合はトランザクションを取り消します。成功時はバックアップ先を表示します。正常なschema 6なら何も変更しないため、再実行してもデータ・設定を初期化しません。不完全な更新済みDBを自動修復する処理ではありません。

既存の管理者・従業員パスワード、給与設定、希望・確定シフト、保存済み休憩分数、初回確定日時、従業員番号の採番履歴は保持します。schema 5の認証版・変更必須フラグもそのままで、この更新によって全員のパスワード変更を強制することはありません。schema 4から認証項目を追加する場合だけ、追加値は認証版0・変更必須0で開始し、旧従業員セッションには再ログインが必要です。新規登録・再発行は、従来どおり本人変更必須の仮パスワード方式です。

更新後は[テストと手動確認](security-and-testing.md)を行い、次のコマンドで再起動します。バックアップにも個人情報とパスワードハッシュが含まれるため、非公開で安全に保管し、配布しないでください。

```powershell
python app.py
```

失敗した場合はDBを削除せず、エラー内容とバックアップの有無を確認してください。復元が必要な場合も、稼働中のDBを上書きせず、アプリを停止して現在のDBを別途保存してから対応します。旧構造のバックアップは、対応する旧コードまたは再度の移行と組み合わせる必要があります。

## 5. DB・秘密情報の取り扱い

通常実行のDB保存先はVer.4内の`instance/shift_management_v4.db`に固定しています。管理者・従業員、希望・割当シフト、店舗設定を保存し、給与形態と個別時給は従業員IDに関連付けた`employee_pay_settings`で雇用区分と独立して管理します。テーブル・制約の詳細は[設計書](../system_design.md)と[schema.sql](../schema.sql)を参照してください。

DBを失うと、登録した管理者・従業員・希望・確定シフト・店舗設定も失われます。DBを再作成しても元データは復元されません。削除・置き換えが必要な場合は、アプリを停止し、必要なバックアップを取得したうえで利用者自身が行ってください。通常の更新や起動のために既存DBを削除する必要はなく、V1～V3のDBを削除する必要もありません。

ソースにパスワード平文や固定管理者パスワードを保存しません。実DB、更新前バックアップ、秘密鍵、管理者パスワード、環境ファイルはGitHubや配布物へ含めないでください。`.gitignore`は既存の追跡やコミット履歴を消さず、手作業のZIPやブラウザアップロードから自動除外する機能でもありません。公開範囲と秘密情報の確認は[セキュリティ・テスト](security-and-testing.md)を参照してください。

## 6. エラー時の確認

| 症状 | 確認内容 |
|---|---|
| SECRET_KEY設定エラー | 同じPowerShellで、32文字以上の`SHIFT_MANAGEMENT_V4_SECRET_KEY`を設定したか。`.env`へ書いただけで済ませていないか |
| Flask／pytestが見つからない | Python環境が正しいか。同じ環境で`python -m pip install -r requirements.txt`を行ったか |
| 仮想環境を有効化できない | Anaconda環境を使うか、`python`を`.\.venv\Scripts\python.exe`へ読み替える。セキュリティ設定の変更は不要 |
| DBが準備されていない（503） | 新規環境ならV4内で`init-db`を行ったか。既存DBなら削除・再作成せず、保存先・DB構造とエラーを確認。V3 DBをコピーしない |
| DB構造の更新が必要（503） | 既存V4は削除せず、アプリ停止後に`migrate-db`を行ったか |
| `init-db`／`migrate-db`がDBを拒否する | V4以外や不完全な構造の可能性。DBを削除・上書きせず、エラー内容を確認 |
| 管理者ログインできない | 初回に`create-admin`を実行したか。自分で登録したユーザー名・パスワードを使っているか |
| 従業員ログインできない | IDは6桁の半角数字か。本人変更後のパスワードか。再発行されていないか。在籍状態が`active`か |
| 400エラー | フォームを開き直す。古いタブ、ログイン切替後や秘密鍵変更後の画面をそのまま送信していないか |
| 429エラー | ログイン失敗制限の15分間の集計窓が過ぎてから再試行 |
| 希望を登録できない | 対象月に提出期限があり現在が期限以前か。勤務日・30分刻み・開始＜終了を満たすか |
| シフトを変更できない | 管理者として操作しているか。在籍中の従業員で、対象月内・本人の希望範囲内・30分刻み・同日重複なしを満たすか。確定済みでも変更可能。旧DBの場合は先に`migrate-db`を実行 |

画面操作・入力条件は[操作ガイド](usage.md)、テスト手順と安全設定は[セキュリティ・テスト](security-and-testing.md)にまとめています。
