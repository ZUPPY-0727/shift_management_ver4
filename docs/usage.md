# 操作ガイド

1店舗向けのシフト管理システム Ver.4 の操作・計算仕様です。GitHubでのソース公開とWebアプリの公開は別であり、アプリは未デプロイです。起動・環境構築は[セットアップ](setup.md)、内部仕様は[システム設計書](../system_design.md)、テストと安全管理は[テスト・セキュリティ](security-and-testing.md)を参照してください。

本アプリは勤務予定を管理するもので、打刻・実際の休憩取得の記録・正式な給与計算は行いません。本書の確認手順は利用者が練習用データで実施するためのもので、実行済みの結果を示すものではありません。

## 1. 画面・URL・権限

PCで扱いやすいフォームと表を中心とした日本語画面です。従業員の確認画面は狭い幅でも読める構成ですが、全日を並べた月間カレンダーやスマートフォン専用アプリではありません。

| 画面・操作 | URL | HTTPメソッド | 利用者 |
|---|---|---|---|
| ログイン入口 | `/` | GET | 共通 |
| 管理者ログイン | `/admin/login` | GET／POST | 管理者の入口 |
| 従業員ログイン | `/employee/login` | GET／POST | 従業員の入口 |
| ログアウト | `/logout` | POST | ログイン中の利用者 |
| 管理者ホーム | `/admin/home` | GET | 管理者 |
| 従業員一覧・登録・給与編集 | `/admin/employees` | GET／POST | 管理者 |
| 従業員情報編集 | `/admin/employees/<int:employee_id>/edit` | GET／POST | 管理者 |
| 従業員操作の確認・実行 | `/admin/employees/<int:employee_id>/actions/<action>` | GETで確認、POSTで実行 | 管理者 |
| 店舗基本時給設定 | `/admin/store-settings` | GET／POST | 管理者 |
| 店舗共通休憩時間設定 | `/admin/break-settings` | GET／POST | 管理者 |
| 提出期限設定 | `/admin/deadlines` | GET／POST | 管理者 |
| 希望シフト確認 | `/admin/shift-requests` | GET | 管理者 |
| シフト案作成・確定 | `/admin/shifts` | GET／POST | 管理者 |
| 従業員ホーム | `/employee/home` | GET | 従業員 |
| 本人パスワード変更 | `/employee/change-password` | GET／POST | 従業員。初回変更必須状態でも利用可能 |
| 本人の希望シフト登録 | `/employee/shift-requests` | GET／POST | 従業員 |
| 全員の確定シフト・本人の月間集計 | `/employee/confirmed-shifts` | GET | 従業員 |

従業員操作の`<action>`は`retire`（退職）、`restore`（復職）、`delete`（完全削除）、`reset-password`（仮パスワード再発行）です。更新操作はPOST、閲覧・月選択はGETです。ログアウトはURLの直接表示ではなく、共通ヘッダーのボタンから行います。

管理者と従業員は入口・権限を分けています。従業員は他人の希望・備考・時給・予想収入を閲覧できません。全員の確定シフトで共有するのは勤務日、従業員ID、氏名、雇用区分、開始・終了時刻です。本人の日別休憩・実働と月間集計は本人向けに表示します。

画面と権限の実装は[管理者ルート](../routes/admin.py)、[従業員ルート](../routes/employee.py)、[認証ルート](../routes/auth.py)、[共通認可](../decorators.py)を参照してください。

## 2. 従業員登録・アカウント運用

### 新規登録と給与設定

管理者で「従業員管理」を開き、氏名・雇用区分・必要に応じた給与設定を入力します。同姓同名は登録できます。生年月日と初期パスワードは入力せず、管理者がパスワードを手動指定することもできません。

| 雇用区分 | 表示 | 給与形態の初期選択 |
|---|---|---|
| `E` | 社員 | 月給制（`monthly`） |
| `P` | パート | 時給制（`hourly`） |
| `A` | アルバイト | 時給制（`hourly`） |

雇用区分と給与形態は別の設定です。初期選択後も管理者が時給制・月給制を手動で指定できます。時給制のときだけ個別時給欄を表示し、正整数円を入力するか、空欄で店舗基本時給を適用します。店舗基本時給の初期値は1,280円です。

登録成功後、`000001`のような6桁IDと自動生成した20文字の仮パスワードを一度だけ表示します。ID・仮パスワードの各コピーボタンで控え、本人へ安全に伝えてください。コピーが許可されないブラウザでは、選択された文字を`Ctrl+C`でコピーできます。共有端末のクリップボードやコピー先、スクリーンショットに認証情報を残さないよう注意してください。

### 初回ログインと本人のパスワード変更

従業員ログインで6桁の半角数字IDと仮パスワードを入力します。在籍状態が`active`の従業員だけがログインできます。IDや生年月日からパスワードを計算する仕組みはありません。

初回はパスワード変更画面へ移動します。「現在」に仮パスワード、「新しいパスワード」と「確認」に本人が決めた値を入力してください。規則は8～64文字、ASCII英字と半角数字を各1文字以上で、現在と同じ値は使えません。

変更完了までは、パスワード変更とログアウト以外の従業員機能を使えません。ホームや希望登録のURLを直接入力したりPOSTしたりしても回避できません。変更後は従業員ホームに進み、以後は本人が設定したパスワードでログインします。

通常ログイン中も、従業員ホームの「パスワード変更」から同じ画面を利用できます。現在・新規・確認の3項目が必要です。変更後は現在のブラウザのログイン状態を作り直して利用を続けられますが、旧パスワードと他のログインセッションは無効になります。

### 仮パスワードを控え忘れた場合・再発行

仮パスワードは成功したPOSTの結果画面だけに表示します。DB・セッション・ログなどへ平文保存せず、画面を離れた後の再表示はできません。同じ登録・再設定フォームの再送信も、一回限りの操作として拒否します。

控え忘れや本人の失念時は、管理者が一覧の「パスワード再設定」から対象ID・氏名を確認し、新しい仮パスワードを発行します。発行結果を再表示する操作ではありません。再発行前のパスワードとログイン状態は無効になり、新しい仮パスワードでの次回ログイン後も本人変更が必須です。本人が設定したパスワードを管理者に表示・復元する機能はありません。

登録・退職・復職・完全削除・再発行にはCSRFとは別の15分有効・一回限りの確認トークンを使います。使用済み・期限切れのフォームは開き直し、対象を確認してから操作してください。認証情報のコピー先は利用者側で管理が必要です。

### 情報・給与編集、退職・復職・完全削除

「給与情報を編集」では給与設定を変更できます。個別時給を空欄で保存すると個別指定を解除します。月給制へ変更した場合も個別時給は解除され、時給制へ戻しても以前の値は復活しません。

「情報を編集」では氏名・雇用区分・給与設定をまとめて変更できます。従業員IDは変更できず、パスワード変更は別操作です。

| 操作 | 状態・履歴・ログインへの影響 |
|---|---|
| 退職 | `retired`にして退職日時を記録。通常一覧から除外し、新規ログイン・既存セッション・新規シフト割当を停止。給与設定・希望・過去シフトは保持 |
| 復職 | 「退職者一覧」から同じIDで`active`へ戻す。退職前のログイン状態は復活せず、再ログインが必要 |
| 完全削除 | 希望・割当シフトが一件もない従業員だけが対象。編集中（draft）・確定済み（confirmed）の割当がある場合も拒否。履歴の連鎖削除はせず、許可された場合だけ給与設定と従業員を一括削除 |

削除済みIDは再利用しません。退職・復職・完全削除・再発行には対象ID・氏名・操作内容を示す確認画面、必須確認欄と確認ダイアログがあります。JavaScriptを無効にしても確認画面とサーバー検証は必要です。

従業員セッションは認証版`auth_version`を持ち、保護URLごとにDBの在籍状態・認証版と照合します。退職・復職・再発行・本人変更で版を進めるため、古いCookieを再利用しても元のログイン状態は復活しません。既存V4のDB構造更新前の従業員セッションも無効になり、再ログインが必要です。更新前からいる従業員のパスワード自体は保持され、移行だけでは初回変更必須にはしません。

実装は[従業員サービス](../services/employee_service.py)、[認証サービス](../services/auth_service.py)、[給与設定サービス](../services/compensation_service.py)を参照してください。

## 3. 希望提出から月の確定まで

### 提出期限と本人希望

管理者は対象月ごとに「提出期限設定」で日時を登録・更新します。日時は日本時間（`Asia/Tokyo`、JST）として扱い、フォームの期限時刻の初期値は23:59です。動作確認では必ず現在より未来の日時を設定してください。

従業員が本人希望を追加・編集・削除できるのは、対象月に期限が設定され、現在日時が期限以前の場合だけです。期限未設定・期限後は拒否します。

出勤可能な日だけを1件ずつ登録します。出勤不可の入力欄はありません。未登録日は期限前「未入力」、期限後「出勤不可」と扱いますが、自動変換した行をDBへ追加するわけではありません。画面は登録済み希望の一覧と個別入力フォームで、月全日のカレンダーではありません。

希望・シフトとも、勤務日は対象月内、時刻は30分刻み（分00／30）、開始＜終了、同じ従業員・同じ日は1件だけです。日跨ぎ・24:00終了・1日複数勤務は扱いません。本人IDはログインセッションから決め、フォームのIDで他人の希望を選択することはできません。

割当済みシフトが希望時間内に収まらなくなる希望編集や、割当済み希望の削除は拒否します。

### 管理者によるシフト案と確定

1. 「希望シフト確認」で対象月の希望を確認します。
2. 「シフト案作成・確定」で同じ対象月を選び、在籍中（`active`）の希望登録者から割り当てます。本人の希望時間内に収めてください。
3. 月が未作成なら、案の保存時に`draft`で作成します。編集中の予定休憩・実働は現在の店舗ルールでプレビューします。既に確定済みの月へ保存しても`draft`へ戻しません。
4. 内容を確認し、確認欄にチェックして月を確定します。0件の月は確定できません。
5. 確定時は全シフトの休憩を検証・保存し、確定日時と`confirmed`状態をまとめて記録します。途中失敗なら休憩保存と状態更新の両方を取り消します。

初回確定後も、管理者は同じ画面から追加・編集・削除できます。確定解除・再確定の操作は不要で、月の`confirmed`状態と初回確定日時は維持します。

「出勤可能な候補」には、在籍中の従業員が登録した希望のうち、従業員ID・勤務日の組み合わせが未割当のものだけを表示し、未割当件数も案内します。割当の保存に成功すると該当する1件が一覧から消えます。同じ人の別日や別の人の同日は残ります。全件割当済みの場合や候補がない場合は「未割当の候補はありません」と表示します。

シフトを削除すると、その従業員・日付の希望が残っていて在籍中なら候補に戻ります。従業員・勤務日の変更では変更前の組み合わせが候補に戻り、変更先は非表示になります。時間だけの変更では非表示のままです。希望データを削除したり割当済みフラグを保存したりせず、画面を表示するたびに保存済みの割当から判定するため、保存失敗時やページ再読み込み時にも実際の状態を反映します。編集中・確定済みの月で共通の動作です。

### 確定済みシフトの修正

1. 管理者の「シフト案作成・確定」で対象の確定月を選択します。
2. 追加する場合は「出勤可能な候補」から従業員と希望日を選びます。編集する場合は既存行の「編集」を選び、同じ対象月内の勤務日・開始・終了時刻を変更できます。変更先の日付にも本人の希望が必要です。
3. 保存時はactive・希望時間内・30分刻み・開始＜終了・1人1日1勤務を従来どおり検証します。提出期限後でも管理者の勤務編集は可能ですが、希望のない日や希望時間外への割当はできません。
4. 追加・勤務内容の変更時は、その行だけ現在の店舗ルールで予定休憩を再計算し、勤務と一括保存します。未変更の別行や、内容を変えずに保存した行の休憩は再計算しません。
5. 削除する場合は対象を確認し、削除ボタンと確認ダイアログで実行します。最後の勤務を削除した場合も、その月は確定済みのままです。

保存後は、従業員が確定シフト画面を再読み込み・再表示すると、全員の一覧と本人の勤務時間・休憩・実働・予想収入が最新DBから更新されます。既に開いているページへの自動通知・自動再読込はありません。確定月の勤務が0件になれば本人の時間集計と時給制の予想収入は0になり、月給制の収入は引き続き計算対象外です。変更履歴・以前の内容への復元・通知は実装していないため、保存前に対象と内容を確認してください。

従業員の「確定シフト確認」は全員分を勤務日昇順、同日ならE→P→A、同一区分はID昇順で表示します。上部に本人の月間拘束・休憩・実働、時給制なら予想収入を表示し、本人の日別休憩・実働も確認できます。未確定月は本人の時間・収入集計を公開しません。

詳細は[希望サービス](../services/shift_request_service.py)、[シフトサービス](../services/shift_service.py)を参照してください。

## 4. 12ステップの手動確認

初回準備後、利用者が練習用データで実施してください。実データを削除・置換して確認する必要はありません。

1. 初回準備を行い、自分で作成した管理者でログインします。
2. 「従業員管理」でアルバイトを1名登録します。一度だけ表示されるIDと自動発行の仮パスワードをコピーして控えます。
3. 「店舗基本時給設定」で基本時給1,280円を確認します。従業員の個別時給は空欄のままにします。
4. 「休憩時間設定」で初期ルールを確認します。8時間超は60分です。
5. 「提出期限設定」で確認用の対象月を選び、提出期限を現在より未来の日時に設定します。期限時刻は初期値23:59です。
6. ログアウトし、ID・仮パスワードで従業員ログインします。強制表示されるパスワード変更画面で本人用パスワードを設定し、ホームへ進みます。
7. 「希望シフト登録」で同じ対象月を選び、任意の日の09:00～21:00を登録します。出勤可能な日だけを1件ずつ登録します。
8. ログアウトし、管理者で「希望シフト確認」を開いて希望を確認します。
9. 「シフト案作成・確定」で同じ対象月を選び、希望一覧の登録操作から09:00～21:00のシフト案を保存します。予定休憩60分・予定実働11時間を確認します。
10. シフト案の内容を確認し、確認欄にチェックして対象月を確定します。
11. 従業員で再ログインし、「確定シフト確認」で同じ対象月を選びます。本人の拘束12時間、休憩1時間、実働11時間、予想収入15,040円を確認します。
12. 必要に応じて別の従業員や月給制従業員も登録し、全員の確定シフトは見える一方、給与集計は本人分だけであることを確認します。

この例の予想収入は、当該従業員の対象月の確定シフトが上記1件だけで、個別時給なし・店舗基本時給1,280円・予定休憩60分の場合です。

## 5. 休憩・勤務予定時間・予想収入

### 5区分の予定休憩

| 拘束時間 | 区分 | 初期の予定休憩 |
|---|---|---:|
| 6時間未満 | `lt6` | 0分 |
| 6時間ちょうど | `eq6` | 45分 |
| 6時間超～8時間未満 | `gt6_lt8` | 45分 |
| 8時間ちょうど | `eq8` | 60分 |
| 8時間超 | `gt8` | 60分 |

拘束時間は開始から終了まで、予定実働時間は拘束時間から予定休憩を引いた時間です。内部計算は整数分で行い、45分の休憩も扱います。個別シフトへ休憩を手入力せず、店舗共通ルールを使います。

```text
拘束分 = 終了時刻の分数 - 開始時刻の分数
予定実働分 = 拘束分 - 予定休憩分
```

設定画面では区分ごとの選択候補を表示します。負値・拘束時間以上の休憩は許可せず、6時間超～8時間未満は最低45分、8時間超は最低60分です。加えて、休憩を差し引いた実働が6時間超なら休憩45分以上、8時間超なら60分以上という本アプリの入力検証を行います。

6時間ちょうど・8時間ちょうどは「初期値」と「検証下限」を区別します。6時間ちょうどの休憩0分、8時間ちょうどの45分は検証を満たします。また最短30分の勤務にも適用するため、6時間未満区分の共通休憩は30分未満とします。これはアプリの設定・検証仕様の説明です。

`draft`は現在の休憩ルールで計算し、初回確定時に各シフトへ休憩分数を保存します。`confirmed`の表示は保存済みの`shifts.break_minutes`を使うため、店舗ルールの変更だけでは保存値は変わりません。確定後に追加した行、従業員・勤務日・開始・終了のいずれかを変更した行だけは現在のルールで再計算します。他の行と、勤務内容を変えず保存した行の休憩記録は維持します。

### 時給制の予想収入と端数処理

時給制では個別時給を優先し、空欄なら現在の店舗基本時給を使います。本人の確定シフトだけを月集計し、予定実働が1日8時間を超えた部分へ25%の割増を加えます。

```text
通常分 = min(予定実働分, 480)
日8時間超分 = max(予定実働分 - 480, 0)
日概算額 = 通常分 × 適用時給 ÷ 60
         + 日8時間超分 × 適用時給 × 5/4 ÷ 60
月概算額 = 各日概算額の合計を、最後に一度だけROUND_HALF_UP相当で整数円へ四捨五入
```

金額はPython標準ライブラリの`Fraction`（有理数）で厳密に扱います。浮動小数点の誤差や日別切り捨てを避け、円未満の端数は月合計で一度だけ丸めます。

09:00～21:00・予定休憩60分なら、拘束720分から60分を引いて予定実働660分（11時間）です。時給1,280円の場合は次の計算です。

```text
通常8時間 × 1,280円 + 8時間超の3時間 × 1,280円 × 1.25
= 10,240円 + 4,800円
= 15,040円
```

月給制では勤務予定時間だけを集計し、収入欄は「月給制のため計算対象外」と表示します。固定月給額は保存しません。未確定月の予想収入は表示しません。

予想収入は確定シフトと予定休憩に基づく概算であり、実際の給与額とは異なる場合があります。正式な給与額・法定割増賃金を算定するものではありません。週40時間超、月60時間超、深夜、法定休日、変形労働時間制の扱い、各種手当、交通費、税金は計算対象外です。

時給改定履歴は保存しません。休憩の確定時保存とは異なり、過去月も現在の時給で再計算する概算です。給与形態・個別時給・店舗基本時給の変更によって、過去月の収入表示が変わる点に注意してください。

計算の実装は[休憩サービス](../services/break_service.py)、[予想収入サービス](../services/payroll_service.py)を参照してください。

## 6. アカウント運用の7ステップ回帰確認

本節も利用者が練習用データで行う確認です。削除してはいけない実データを対象にしないでください。

1. 管理者で従業員を新規登録し、入力フォームにパスワード欄がなく、結果にID・仮パスワードとコピー操作があることを確認します。
2. 結果画面から一覧へ戻り、仮パスワードが再表示されないことを確認します。同じPOSTの再送信は拒否され、新規従業員が増えないことも確認します。
3. 別ブラウザでその仮パスワードを使ってログインし、ホームや希望登録のURLを直接入力しても変更画面へ戻ることを確認します。本人変更を終えるとホームへ進めます。
4. 管理者で氏名・雇用区分・給与設定を編集し、IDが変わらないこと、月給への変更で個別時給が解除されることを確認します。
5. 従業員をログインさせたまま、管理者で対象の「パスワード再設定」を確認・実行します。従業員側の次の操作がログインへ戻ること、旧パスワードではログインできないことを確認します。新しい仮パスワードでは再度変更が必須になります。
6. 「退職」を確認・実行し、通常一覧から消えること、退職者一覧と過去シフトには残ること、ログインできないことを確認します。「復職」で同じIDのまま利用を再開できますが、退職前のセッションは使えません。
7. 完全削除の練習は別の履歴なし従業員で行います。対象ID・氏名を確認して削除し、次の登録でその番号が再利用されないことを確認します。希望・割当シフトのある従業員では完全削除が拒否されます。

通常の本人変更も、現在・新規・確認を入力して確認してください。変更したブラウザは利用を続けられ、旧パスワードや別ブラウザの古いログイン状態が使えなくなることが確認点です。

## 7. 操作で困ったとき

| 症状 | 確認すること |
|---|---|
| 管理者ログインできない | 初回準備で自分の管理者を作成したか。そのユーザー名・パスワードか。固定デモアカウントはありません |
| 従業員ログインできない | IDは6桁の半角数字か。本人変更後のパスワードか。再発行されていないか。在籍中（active）か |
| ホームや希望登録へ進めない | 初回・再発行後のパスワード変更が未完了でないか。先に本人変更を完了します |
| パスワード変更に失敗する | 現在の値、新規8～64文字・ASCII英字と半角数字を各1文字以上、確認一致、現在と異なる値を確認 |
| 仮パスワードを再表示できない | 一度だけの表示です。管理者が対象を確認し、新しい仮パスワードを再発行します |
| コピーできない | ブラウザでコピーが許可されているか。選択された文字をCtrl+Cでコピーし、共有端末に残さないようにします |
| 400エラー | 古いタブ、ログイン切替・秘密鍵変更後の画面、期限切れ・使用済みの確認フォームを送っていないか。フォームを開き直して再操作 |
| 429エラー | ログイン失敗などの制限です。15分の集計窓が過ぎてから再試行。現在パスワードの照合失敗にも制限があります |
| 希望を登録・編集・削除できない | 対象月の期限が設定済みで、現在が期限以前か。勤務日・30分刻み・開始＜終了・同日重複を確認。割当済み希望の削除や希望範囲の縮小も制限されます |
| シフトを追加・編集できない | 管理者か、activeの希望登録者か、希望時間内か、対象月内か、30分刻み・開始＜終了・同日重複なしを満たすか。勤務日変更時は変更先の日にも本人希望が必要。確定済みでも管理者は同じ条件で変更可能 |
| 月を確定できない | 1件以上のシフトがあるか、確認欄にチェックしたか、店舗休憩設定が検証を満たすか |
| 完全削除できない | 希望またはdraft／confirmedの割当が一件でもないか。履歴を残す場合は退職を使います |
| 過去月の予想収入が変わった | 現在の給与形態・時給を使う概算です。時給履歴は保存しません。確定済み休憩の保存とは別の仕様です |
| DB未準備・DB構造更新が必要（503） | [セットアップ](setup.md)の準備案内を確認。既存V4 DBは削除せず、アプリ停止後に構造更新します。V3 DBをコピーして代用しないでください |

環境構築は[セットアップ](setup.md)、秘密情報・テスト実行は[テスト・セキュリティ](security-and-testing.md)、詳細な制約や保存方式は[システム設計書](../system_design.md)を参照してください。[README](../README.md)では開発の背景と設計判断を紹介しています。

## 8. 確定後編集の手動確認

1. 練習用従業員で、同じ月の複数日に十分な希望時間を登録し、一部の勤務だけを案にして確定します。
2. 管理者が提出期限を過去に変更してから、残りの希望日へ勤務を追加します。月は確定済みのままで、従業員の再表示で一覧・本人集計が増えることを確認します。
3. 休憩設定を変更し、既存勤務の時間または勤務日を変更します。変更した行だけ新しい休憩値となり、別の未変更行は保存済みの値を維持することを確認します。
4. 内容を一切変えず既存勤務を保存し、その行の休憩値も維持されることを確認します。
5. 勤務を削除し、確認ダイアログと、従業員の次回表示で一覧・本人集計が減ることを確認します。最後の1件を削除しても確定状態は維持します。
6. 希望時間外・30分刻み以外・開始≧終了・月外・重複を送信すると拒否され、不完全な変更が残らないこと、従業員から管理者用URL・POSTを利用できないことを確認します。

これは実行済みの結果ではなく、利用者が架空データで実施する確認手順です。デモで使った15,040円の例は対象月1勤務の条件なので、編集・追加後の期待額は最新の勤務と設定から確認してください。
