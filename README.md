# シフト管理システム Ver.4

1店舗向けの、Python・Flask・SQLite製Webシフト管理システムです。Ver.3のログイン、希望提出、シフト作成・確定の流れを引き継ぎ、給与形態・時給・店舗共通の予定休憩ルールと、本人の月間勤務予定・予想収入の表示を追加しています。

現段階はローカル環境で確認するためのV4です。Web公開、クラウド配備、PostgreSQLへの移行、QRコードの発行は別工程で行います。

このリポジトリの対象はVer.4のソースコードだけです。実際の従業員情報・アカウント・SQLite DB・秘密鍵は同封しません。GitHubへソースを置くことと、Webアプリをインターネットへ公開することは別であり、今回は前者の準備だけを行います。[GitHub公開前の確認](#15-github公開前の確認)も参照してください。

## 1. V3との違い

- 氏名は表示・識別の補助として保持し、生年月日は収集・保存しません。従業員IDは6桁表示を維持します。
- 従業員管理画面で、給与形態と個別時給を登録・編集できます。
- 社員は月給制、パート・アルバイトは時給制を初期選択します。管理者は変更できます。
- 店舗基本時給の初期値は1,280円です。個別時給が空欄なら店舗基本時給を適用します。
- 休憩は店舗共通の5区分ルールで自動計算し、月の確定時に各シフトへ保存します。
- 確定シフト確認画面で、本人の勤務予定時間と予想収入を確認できます。
- V4のDB・管理者・従業員は新規作成します。V1～V3のデータ移行は行いません。
- 希望勤務上限・収入上限・扶養判定・必要人数設定・人数不足表示は、V4の開発対象に含めません。

V1・V2・V3のソースやDBは、本アプリから変更しません。V3のDBをV4のDBとしてコピーしたり、初期化対象に指定したりしないでください。

## 2. 使用技術と目的

使用技術はPython、Flask、Werkzeug、Click、SQLite、HTML／Jinja2、CSS、JavaScript、pytestです。Werkzeugはパスワードのハッシュ化、ClickはFlask CLIコマンドに使用します。SQLite接続、日時、正確な金額計算にはPython標準ライブラリを使用します。

既存のシフト業務をブラウザから操作し、勤務予定に基づく時間・収入の目安を確認することが目的です。勤怠の打刻や実際の休憩取得の記録、正式な給与計算を行うシステムではありません。

## 3. 主な機能

| 利用者 | できること |
|---|---|
| 管理者 | 管理者ログイン、従業員登録、給与形態・個別時給編集、基本時給設定、予定休憩設定、提出期限設定、希望確認、シフト案の追加・編集・削除、月単位の確定 |
| 従業員 | 従業員ログイン、期限内の本人希望の追加・編集・削除、全員の確定シフト確認、本人の月間勤務予定・予想収入確認 |

従業員管理には氏名・雇用区分・給与設定の編集、退職・復職、履歴のない従業員の完全削除、仮パスワード再発行があります。新規登録と再発行は安全な仮パスワードの自動発行に統一し、本人の初回変更を必須とします。本人は通常ログイン中もパスワードを変更できます。

ログイン入口と権限を管理者・従業員で分けています。従業員は他人の希望や備考、時給、予想収入を閲覧できません。全員の確定シフトに表示する情報は、勤務日、従業員ID、氏名、雇用区分、開始・終了時刻です。

## 5. 必要な環境

- Python 3.10以降
- PowerShellまたはAnaconda PowerShell Prompt
- ローカルブラウザ

Pythonを使える環境を有効にし、以降の操作は`shift_management_ver4`フォルダ内で実行します。既存のV3フォルダと間違えないようにしてください。

```powershell
cd C:\projects\shift_management_ver4
```

上記は配置先の例です。実際にダウンロード・配置したVer.4フォルダへ読み替えてください。独立リポジトリをcloneした場合は、そのリポジトリ直下に`app.py`がある状態で作業します。

## 6. 初回の準備と起動

### 6.1 必要なライブラリをインストールする

既にAnaconda等の専用Python環境がある場合は、その環境を有効にして使用してください。新しいPCでは、任意で以下の仮想環境を作成できます（Ver.4フォルダ内で実行）。

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

PowerShellの設定により有効化できない場合は、既存のAnaconda環境を使うか、以降の`python`を`.\.venv\Scripts\python.exe`に読み替えてください。セキュリティ設定を変更する必要はありません。

使用するPython環境で必要な依存関係をインストールします。

```powershell
python -m pip install -r requirements.txt
```

`pip install -r requirements.txt`も利用できますが、上記なら選択中のPython環境へインストールできます。`requirements.txt`にはFlask、直接importするWerkzeug・Click、自動テスト用のpytestを記載しています。Werkzeug・ClickはFlaskの依存にも含まれます。SQLite、secrets、pathlib等の標準ライブラリや、未使用のPostgreSQLドライバー等は追加していません。

requirementsのバージョン指定は完全固定のロックファイルではありません。別PCでの再現性や将来の更新時には、テストの再実行と依存バージョンの確認が必要です。

### 6.2 セッション用の秘密鍵を設定する

V4には固定の開発用キーがありません。以下はPowerShell用です。`set "変数=値"`というコマンドプロンプトの書き方とは異なります。

```powershell
$env:SHIFT_MANAGEMENT_V4_SECRET_KEY = python -c "import secrets; print(secrets.token_hex(32))"
```

上記は生成したランダム文字列をそのPowerShellの環境変数に設定します。生成した秘密値をREADME、ソース、GitHubへ貼り付けないでください。

新しいPowerShellを開いたときは再設定が必要です。キーを変更すると既存のログインセッションは無効になり、再ログインが必要になります。継続運用時は適切な秘密情報管理の方法で同じ安全なキーを設定します。

### 6.3 新しいV4データベースを準備する

```powershell
python -m flask --app app:create_app init-db
```

V4のテーブル、基本時給1,280円、休憩ルールが作成されます。管理者・従業員・シフトのデモデータは自動登録されません。現行構造への初期化コマンドの再実行でも既存の業務データや設定は消しませんが、旧構造の既存V4は初期化を拒否し、次の`migrate-db`を案内します。

V4以外の構造のDBが見つかった場合は、誤上書きを避けるためエラーにします。

### 6.4 自分で管理者を作成する

```powershell
python -m flask --app app:create_app create-admin --username manager
```

`manager`は一例です。自分が使用する管理者名へ変更できます。管理者パスワードと確認用パスワードを非表示入力します。

パスワード規則は8～64文字、ASCII英字を1文字以上、数字を1文字以上です。V3で公開したデモ用パスワード系統は管理者作成時に拒否します。新しいパスワードを設定してください。

固定の管理者ID・パスワードはありません。以後は、自分で作成したユーザー名・パスワードで管理者ログインします。管理者登録画面とデモ従業員作成CLIはありません。

管理者パスワードは、必要なら環境変数`SHIFT_MANAGEMENT_V4_ADMIN_PASSWORD`からも渡せます。通常は非表示入力を推奨します。使用後は`Remove-Item Env:SHIFT_MANAGEMENT_V4_ADMIN_PASSWORD`で現在のPowerShellから解除できます。

### 6.5 起動する

```powershell
python app.py
```

ブラウザで次を開きます。

```text
http://127.0.0.1:5000
```

終了するときは起動中のPowerShellで`Ctrl+C`を押します。ローカル起動は`127.0.0.1`に限定し、debugは無効です。

2回目以降は、必要なPython環境・秘密鍵を準備して`python app.py`を実行します。DBが存在する場合、毎回の初期化や管理者再作成は不要です。

### 6.6 既にV4を使用している場合の更新（今回の変更）

既存DBを削除したり、初回準備をやり直したりしないでください。アプリを`Ctrl+C`で停止し、いつものPython環境・秘密鍵を準備した同じPowerShellで実行します。

```powershell
python -m flask --app app:create_app migrate-db
```

内部DB構造をschema 4から5に更新します（製品名はVer.4のままです）。従業員の認証版・パスワード変更必須フラグ、従業員ID変更禁止トリガー、一度限りの発行操作を管理する`one_time_tokens`を追加します。業務テーブルの削除・再作成、アカウントやシフトの初期化はしません。

更新前のDBは`instance/backups/before_employee_accounts_*.db`へ自動保存し、保存・整合性確認に失敗すれば構造更新を中止します。更新途中の失敗時はトランザクションを取り消します。成功時にはバックアップ先が表示され、更新済みの場合は何も変更しません。バックアップにも個人情報・ハッシュが含まれるため、安全に保管して配布しないでください。

既存の管理者・従業員パスワード、給与、希望・確定シフトと休憩記録、従業員番号の採番履歴は保持します。移行前の従業員は変更必須にはせず、既存パスワードで利用できます。従業員の旧ログインセッションは無効になり、再ログインが必要です。移行後の新規登録・再発行は必ず仮パスワード方式です。更新後は下記テストと手動確認を行い、`python app.py`で再起動します。

更新に失敗した場合はDBを削除せず、エラー内容とバックアップの有無を確認してください。復元が必要な場合も、稼働中のDBを上書きせずアプリを停止し、現在のDBを別途保存してから対応します。旧構造のバックアップは対応する旧コードまたは再度の移行と組み合わせる必要があります。

## 8. 従業員の登録・ログイン方法

管理者でログインし、「従業員管理」で氏名、雇用区分、必要に応じた給与設定を入力して登録します。生年月日と初期パスワードは入力しません。管理者によるパスワード手動指定は廃止しました。

雇用区分は`E：社員`、`P：パート`、`A：アルバイト`です。給与形態は区分に応じて自動選択されますが、手動で時給制・月給制を指定できます。時給制のときだけ個別時給欄を表示します。空欄なら店舗基本時給を使います。

登録後、`000001`のような6桁IDと、自動生成した20文字の仮パスワードを一度だけ表示します。各コピーボタンで控え、本人へ安全に伝えてください。コピーが許可されないブラウザでは選択された文字をCtrl+Cでコピーできます。コピー内容を共有端末に残さないよう注意してください。生年月日やIDからパスワードを計算する仕組みはありません。

従業員ログインでは、6桁の半角数字IDと仮パスワードを入力します。在籍状態が`active`の従業員だけが利用できます。初回は必ずパスワード変更画面に移動し、現在欄に仮パスワード、新しいパスワードと確認欄に本人が決めた値を入力します。変更完了まで希望提出などの通常機能は利用できません。変更後は従業員ホームに移動し、以後は新しいパスワードでログインします。規則は8～64文字、ASCII英字と半角数字を各1文字以上で、現在と同じ値は使えません。

仮パスワードはDB・セッション・ログに平文保存しません。画面を離れた後の再表示や、同じ登録・再設定フォームの再送信による再発行はできません。控え忘れた場合は、一覧の「パスワード再設定」から対象ID・氏名を確認し、新しい仮パスワードを発行してください。新旧どちらの発行でも次回変更が必須で、再発行前のパスワードとログイン状態は無効です。本人が設定済みのパスワードは管理者にも表示できません。

通常の本人変更は従業員ホームの「パスワード変更」から行います。現在・新規・確認の3項目が必要です。変更後も現在のブラウザは利用できますが、他のログインセッションは無効になります。

登録済み従業員の給与は、一覧の「給与情報を編集」から変更できます。個別時給は空欄で保存すると解除します。月給制にすると個別時給は解除され、時給制へ戻しても古い個別時給は復活しません。

一覧の「情報を編集」では氏名・雇用区分・給与設定をまとめて変更できます。従業員IDは変更できず、パスワードは別操作です。「退職」は履歴を残してログインと新規シフト割当を停止し、通常一覧から除外します。「退職者一覧」で確認・復職できます。復職しても退職前のログイン状態は復活しません。「完全削除」は希望・割当シフト（編集中を含む）が一件もない場合だけ許可し、給与設定も一括削除します。削除したIDは再利用しません。退職・復職・削除・再設定はいずれも確認画面と確認操作が必要です。

## 9. 短時間で確認する手順

1. 初回準備を行い、自分で作成した管理者でログインします。
2. 「従業員管理」でアルバイトを1名登録します。一度だけ表示されるIDと自動発行の仮パスワードをコピーして控えます。
3. 「店舗基本時給設定」で基本時給1,280円を確認します。従業員の個別時給は空欄のままにします。
4. 「休憩時間設定」で初期ルールを確認します。8時間超は60分です。
5. 「提出期限設定」で確認用の対象月を選び、提出期限を現在より未来の日時に設定します。期限時刻は初期値23:59です。
6. ログアウトし、ID・仮パスワードで従業員ログインします。強制表示されるパスワード変更画面で本人用パスワードを設定し、ホームへ進みます。
7. 「希望シフト登録」で同じ対象月を選び、任意の日の09:00～21:00を登録します。出勤可能な日だけを1件ずつ登録します。
8. ログアウトし、管理者で「希望シフト確認」を開いて希望を確認します。
9. 「シフト案作成・確定」で同じ対象月を選び、希望一覧の登録操作から09:00～21:00のシフト案を保存します。予定休憩60分・予定実働11時間を確認します。
10. シフト案の内容を確認し、確認欄にチェックして対象月を確定します。
11. 従業員で再ログインし、「確定シフト確認」で同じ対象月を選びます。本人の拘束12時間、休憩1時間、実働11時間、予想収入15,040円を確認します。
12. 必要に応じて別の従業員や月給制従業員も登録し、全員の確定シフトは見える一方、給与集計は本人分だけであることを確認します。

確定後はその月を追加・編集・削除できません。やり直しの練習は別の対象月を使用してください。希望時刻・シフト時刻はすべて30分刻みで、同一従業員・同一日には1件だけ登録できます。

## 10. 休憩・勤務時間・収入の計算

| 拘束時間 | 初期の予定休憩 |
|---|---:|
| 6時間未満 | 0分 |
| 6時間ちょうど | 45分 |
| 6時間超～8時間未満 | 45分 |
| 8時間ちょうど | 60分 |
| 8時間超 | 60分 |

拘束時間は開始から終了までの時間、予定実働時間は拘束時間から予定休憩を引いた時間です。内部計算は整数分で行い、45分の休憩も扱います。休憩は個別シフトに手入力せず、店舗共通ルールを使用します。

draftでは現在の休憩ルールで計算し、確定時に各シフトの休憩分数を保存します。後から店舗のルールを変更しても、確定済みシフトの休憩集計は変わりません。

時給制の予想収入は、個別時給があればそれを優先し、なければ現在の店舗基本時給を使います。予定実働が1日8時間を超えた部分には25%の割増を加えます。

```text
通常分 = min(予定実働分, 480)
割増対象分 = max(予定実働分 - 480, 0)
予想額 = 通常分 × 時給 ÷ 60 + 割増対象分 × 時給 × 1.25 ÷ 60
```

円未満の端数は日別に切り捨てず、月合計に対して一度だけ四捨五入します。月給制では勤務予定時間のみを集計し、収入欄は「月給制のため計算対象外」と表示します。未確定月の予想収入は表示しません。

予想収入は確定シフトと予定休憩時間から計算した概算です。実際の給与額とは異なる場合があります。正式な給与額・法定割増賃金を算定するものではありません。週40時間超、月60時間超、深夜、法定休日、変形労働時間制の扱い、各種手当、交通費、税金は計算対象外です。時給改定履歴は保存せず、過去月も現在の時給で概算します。

## 11. DB・秘密情報の扱い

使用DBは`instance/shift_management_v4.db`です。初回の`init-db`で作成し、通常起動時に未初期化DBを自動作成することはありません。DBがない場合はREADMEに従って準備するよう案内します。

DBを失うと登録した管理者、従業員、希望、確定シフト、店舗設定は失われます。DBを再作成しても元データは復元されません。DBの削除・置き換えはアプリを停止し、必要なバックアップを取得したうえで利用者自身が行ってください。V1～V3のDBを削除する必要はありません。

給与形態と個別時給は、従業員IDに関連付けた`employee_pay_settings`に保存します。雇用区分とは独立しています。ソース内にpassword平文や固定管理者passwordを保存しません。

`.gitignore`はキャッシュ、仮想環境、`.env`、実DBなどを対象にします。ただし、手作業で作るZIPから自動除外する機能ではありません。配布時は実データ入りDB、秘密鍵、環境ファイルを含めないことを確認してください。

6. 「退職」を確認・実行し、通常一覧から消えること、退職者一覧と過去シフトには残ること、ログインできないことを確認します。「復職」で同じIDのまま利用を再開できます。

## 13. エラー時の確認

| 症状 | 確認内容 |
|---|---|
| SECRET_KEY設定エラー | 同じPowerShellで32文字以上の`SHIFT_MANAGEMENT_V4_SECRET_KEY`を設定したか |
| Flask／pytestが見つからない | Python環境が正しいか、同じ環境で`pip install -r requirements.txt`したか |
| DBが準備されていない | V4内で`init-db`を実行したか。V3 DBをコピーしていないか |
| DB構造の更新が必要（503） | 既存V4は削除せず、アプリ停止後に`migrate-db`を実行したか |
| 管理者ログインできない | `create-admin`を実行したか。自分で登録したユーザー名・passwordを使用したか |
| 従業員ログインできない | IDは6桁の半角数字か。変更後のpasswordか。再発行されていないか。active状態か |
| 400エラー | フォームを開き直して再操作。古いタブ、ログイン切替後の画面、秘密鍵変更後の画面をそのまま送信していないか |

| 希望を登録できない | 対象月に提出期限があり、現在が期限以前か。勤務日・30分刻み・開始＜終了を満たすか |
| シフトを変更できない | 希望範囲内か。同日重複でないか。すでに確定済みでないか |

## 14. 安全設定と今後の対象

全POSTにはCSRF検証を適用し、パスワードをハッシュ保存します。保護URLでは利用者の存在と在籍状態を毎回照合します。ログイン失敗はアカウント単位で5回、接続元単位で30回を15分間の窓で制限し、HTTP 429を返します。CookieはHttpOnly、SameSite=Lax、セッションの有効期間は8時間です。

ローカルHTTPではSecure属性を無効にしています。将来HTTPS公開する際は`SHIFT_MANAGEMENT_V4_COOKIE_SECURE=true`を設定し、開発用サーバーの置き換え、HTTPS、秘密情報管理、バックアップ、アクセス制御、運用監視などの確認を別途行います。

今回の対象外は、Web公開、QRコード、PostgreSQL、日跨ぎ／24:00終了、1日複数勤務、確定解除、勤怠記録、正式な給与計算、給与改定履歴、管理者代理希望入力、管理者本人のパスワード変更画面、AI自動作成、CSV／PDF、メール、複数店舗です。

希望勤務上限・収入上限・扶養判定・必要人数管理・人数不足表示は、将来追加の予定にも含めず、今回のV4から除外しています。

### リポジトリ作成後に利用者が確認するコマンド

以下は有効なリポジトリが用意された後に使う読み取り専用の確認です。実行元はVer.4フォルダとし、`git rev-parse`の結果がそのフォルダ自身であることを確認します。親ワークスペースが出た場合は、そのまま追加・コミットしないでください。
