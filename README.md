# シフト管理システム Ver.4

アルバイト先のシフト管理業務を題材に、**希望提出からシフト案の作成・月単位の確定までを一元管理するWebシステム**を開発しました。管理者と従業員で利用できる機能を分け、従業員本人は確定した勤務予定と予想収入も確認できます。

現在はPython・Flask・SQLiteによるローカル版です。GitHubでソースコードを公開していますが、Webアプリ自体はまだデプロイしていません。

## 1. プロジェクト概要

- 対象：1店舗・日本語・PCブラウザ優先のシフト管理
- 管理者：従業員管理、提出期限設定、希望確認、シフト案作成・確定
- 従業員：希望日時の登録、全員の確定シフト閲覧、本人の予定時間・予想収入の確認
- 位置付け：授業発表用Web版を基礎に、要件と安全性を見直しながら改善している成果物

勤怠の打刻や勤務実績を記録するものではなく、予定に基づく管理を対象としています。実店舗への導入実績や、作業時間の削減率などの未確認の成果は掲載していません。

## 2. 開発背景・解決したい課題

アルバイト先のシフト管理業務を題材に、「いつまでに希望を出すか」「誰をどの時間に割り当てられるか」「確定後に何を共有するか」を一つの流れとして扱える仕組みを目指しました。

要件を整理するうえで、特に次の点を重視しました。

- 希望の受付と管理者の割当を分け、本人の希望時間外への割当を防ぐこと
- 提出期限と編集中・確定済みの状態を明確にし、変更可能な範囲を分かりやすくすること
- 全員で共有する確定シフトと、本人・管理者だけが扱う希望や給与情報を分けること
- 管理者の業務だけでなく、従業員が自分の勤務予定・収入の目安を把握できること

単に画面を増やすのではなく、業務の制約を整理し、それを権限・状態・入力検証へ落とし込むことを開発の軸にしています。

## 3. 画面イメージ・操作デモ

スクリーンショットは準備中です。後から架空の従業員データで撮影した画像を追加します。現時点では画像・動画のファイルや公開デモURLがないため、リンクは設けていません。

### 管理者用画面

- シフト案作成・確定：従業員の希望を確認し、希望範囲内で勤務を登録して月単位で確定する画面
- 従業員管理：氏名・雇用区分・給与形態・在籍状態と、編集・退職等の操作を確認する画面

### 従業員用画面

- 希望シフト登録：対象月を選び、出勤可能な日と時間だけを登録する画面
- 確定シフト確認：全員の確定シフトと、本人の月間予定時間・予想収入を確認する画面

### 操作デモ

動画も準備中です。「従業員登録 → 希望提出 → 管理者による割当・確定 → 従業員による確認」の流れを想定しています。ローカルで試す場合は[操作ガイドとデモ確認手順](docs/usage.md)を参照してください。

撮影では実在の氏名・勤務予定・給与情報を使わず、パスワード、秘密鍵、Cookie、通知やローカルの個人用パスも映さないようにします。

## 4. 主な機能と利用の流れ

| 利用者 | 主な機能 |
|---|---|
| 管理者 | 従業員の登録・情報編集・退職・復職、履歴なし従業員の完全削除、仮パスワード再発行 |
| 管理者 | 給与形態・個別時給、店舗基本時給・予定休憩ルール、月ごとの提出期限の設定 |
| 管理者 | 対象月の希望確認、シフト案の追加・編集・削除、月単位の確定、確定状態のまま勤務を修正 |
| 従業員 | 初回・再発行後の必須パスワード変更、通常の本人パスワード変更 |
| 従業員 | 提出期限内の本人希望の追加・編集・削除 |
| 従業員 | 全員の確定シフト閲覧、本人だけの予定時間・予想収入の確認 |

基本の利用手順は次のとおりです。

1. 管理者が従業員を登録し、自動発行されたID・仮パスワードを本人へ伝える。
2. 従業員が初回ログイン後に自分のパスワードへ変更する。
3. 管理者が対象月の提出期限を設定する。
4. 従業員が出勤可能な日時を1件ずつ登録する。
5. 管理者が希望時間内でシフト案を作成・確認し、月単位で確定する。
6. 従業員が確定シフトと本人の集計を確認する。

1人1日1勤務、開始・終了は30分刻みです。期限後の従業員による希望変更や、希望時間外への割当を制限しています。管理者は提出期限後・確定後も、本人が登録済みの希望時間内で勤務を追加・編集・削除できます。詳しい入力規則・URL・エラー時の確認は[操作ガイド](docs/usage.md)にまとめています。

## 5. 要件定義・設計上の工夫

### 必要な個人情報と、識別に必要な情報を分ける

氏名は管理者が対象者を見分けるために残し、一意の識別には自動採番の従業員IDを使います。同姓同名を許可し、雇用区分を変えてもIDは変わりません。一方、現在の業務に不要な生年月日はVer.4で収集・保存しない設計にしました。

雇用区分と給与形態も同一視せず、給与設定を従業員IDに結び付けた別テーブルで管理しています。

### 画面の出し分けだけでなく、サーバー側で権限を確認する

管理者・従業員でログイン入口を分け、保護されたURLごとにロール・在籍状態・認証情報のバージョンをDB照合します。従業員本人の操作対象はセッションから決め、フォームで他人のIDを指定しても本人用の処理対象にしません。

全員の確定シフトは共有しますが、他人の希望・備考・時給・予想収入は公開しない境界を設けています。

### 仮パスワード方式へ見直す

従業員登録時に管理者が初期パスワードを考える方式を廃止し、登録・再発行に共通の安全な乱数生成処理を使います。仮パスワードは一度だけ表示し、DBへはハッシュだけを保存します。

初回・再発行後は本人変更が終わるまで通常機能を使えないようにし、再発行後の旧セッションも無効化します。管理者でも本人の設定済みパスワードは閲覧できません。

### 状態と履歴を守る

シフトは「編集中」と「確定済み」を月単位で管理します。希望の有無・時間範囲・重複を検証し、確定後も管理者が同じ画面で勤務を修正できます。DB制約・トリガーでは勤務月の一致、確定勤務の休憩記録、確定状態・初回確定日時の保持を補助します。

退職は履歴を残す論理削除とし、完全削除は業務履歴がない場合だけに限定します。DB構造の更新も、バックアップとトランザクションを用いて既存V4のデータを保持する方針です。

### デモで分かった「確定後に修正できない」制約を改善する

実際のデモ操作で、一度確定すると追加・編集・削除ができず、誤確定や予定変更に対応できないことが分かりました。そこで、確定解除や再確定の画面を増やすのではなく、確定状態のまま管理者が既存画面で修正できるように変更しました。保存した内容は従業員の次回表示にも反映され、本人の勤務時間・休憩・予想収入を最新の勤務から集計します。変更履歴・復元・通知は今回追加していません。

### 予定休憩・予想収入を、計算の前提と一緒に示す

勤務時間は整数の分単位、金額はPython標準の`Fraction`で計算し、月合計の最後に一度だけ円未満を四捨五入します。予定休憩は各確定シフトに保存し、店舗の休憩設定変更だけでは保存値を変えません。確定後に追加・勤務内容を変更した行だけは現在のルールで再計算し、変更していない行と、内容を変えず保存した行の休憩記録は維持します。

予想収入は時給制の本人分だけを対象とし、1日の予定実働8時間超に25%を加える簡易計算です。週・月単位、深夜・休日等の割増、税・手当は扱わず、正式な給与計算ではないことを明示しています。時給履歴は固定保存せず、過去月も現在の時給による概算です。[計算例と制限事項](docs/usage.md)を参照してください。

### 実装しない機能も要件として決める

希望勤務上限・希望収入上限・扶養判定・必要人数管理・人数不足表示は、Ver.4および今後の対象から除外しました。管理対象と検証範囲を絞り、希望提出から確定までの一連の流れと、本人の予定確認を優先しています。

詳細な確定仕様・テーブル・制約・URLは[システム設計書](system_design.md)にまとめています。

## 6. Ver.1〜Ver.4の開発の変遷

| バージョン | 既存資料から確認できる内容 |
|---|---|
| Ver.1 | 旧版として別フォルダに保持。READMEに本文がないため、独自の機能・技術の詳細は記載していません。 |
| Ver.2 | Python・SQLite製のCLI版。Ver.3の設計書・READMEに、Web化の参考元として記載されています。 |
| Ver.3 | 授業発表用のFlask製Webプロトタイプ。従業員登録、提出期限、希望提出、管理者による案作成・確定、従業員による確定シフト確認をブラウザへ展開しました。 |
| Ver.4 | Ver.3の業務フローを基礎に、個人情報・給与設定の見直し、予定休憩・予想収入、従業員管理と仮パスワード方式を追加・改善しました。現在の公開対象です。 |

沿革の根拠は、開発時に参照した旧版資料（`shift_management_ver3/README.md`、同`system_design.md`）と、現行の[設計書](system_design.md)です。Ver.1・Ver.2のREADMEは本文がなく、特にVer.1については推測で補っていません。旧版資料・ソース・DBはこのVer.4リポジトリには含めていません。

Ver.4では旧版のソースを参考にしていますが、Ver.1〜Ver.3のデータを引き継がず、専用DBを新規に作成する方針です。これは、既存Ver.4内部のデータを保つマイグレーションとは別の扱いです。

## 7. 使用技術・システム構成

| 分野 | 使用技術・用途 |
|---|---|
| バックエンド | Python 3.10以降、Flask |
| 画面 | HTML / Jinja2、CSS、必要最小限のJavaScript |
| データベース | SQLite、Python標準の`sqlite3` |
| 認証・CLI | Werkzeugによるパスワードのハッシュ化、Flaskセッション、Click |
| 計算・乱数 | 整数分、`Fraction`、`secrets` |
| 自動テスト | pytest、Flaskテストクライアント、一時SQLite DB |

処理は次のように分けています。

```text
ブラウザ
  ↓
routes          HTTP入力・権限適用・画面への受け渡し
  ↓
services        入力検証・業務ルール・計算・トランザクション
  ↓
repositories    SQLによる取得・更新
  ↓
SQLite
```

画面処理と業務ルール、SQLを分離して変更箇所を追いやすくしています。ただし、PostgreSQLへの移行は接続先を変えるだけではなく、SQLite固有のSQL・制約・初期化処理等の見直しが必要です。

主な参照先は、起動・設定の[app.py](app.py)／[config.py](config.py)、DB定義の[schema.sql](schema.sql)、業務処理の[services/](services/)、SQLの[repositories/](repositories/)です。

## 8. 環境構築・実行方法

ローカル実行にはPython 3.10以降が必要です。以下はPowerShellでの**新規環境向け**の最短手順です。Pythonの専用環境を有効にしてから実行してください。

```powershell
git clone https://github.com/ZUPPY-0727/shift_management_ver4.git
cd shift_management_ver4
python -m pip install -r requirements.txt
$env:SHIFT_MANAGEMENT_V4_SECRET_KEY = python -c "import secrets; print(secrets.token_hex(32))"
python -m flask --app app:create_app init-db
python -m flask --app app:create_app create-admin --username manager
python app.py
```

ブラウザで `http://127.0.0.1:5000` を開きます。これはローカルのアクセス先であり、公開デモURLではありません。`manager`は作成する管理者名の例で、パスワードは非表示の確認付き入力で本人が設定します。固定の管理者アカウント・パスワード・実データ入りDBは配布していません。

既存のV4データがある場合は、DBを削除したり初回手順をやり直したりせず、[既存V4の更新手順](docs/setup.md)を参照してください。仮想環境、新しいターミナルでの秘密鍵設定、DBバックアップ、`migrate-db`、トラブル対応も同文書に記載しています。

## 9. テスト・セキュリティ

pytestによるサービス・CLI・Web操作の自動テストを用意しています。一時DBを使い、実際の従業員データや通常運用のDBと分離しています。WebテストでもCSRF対策を無効化せずに検証する構成です。

主な検証対象は、認証・ロール、初回変更強制と旧セッションの無効化、従業員管理、希望の期限・時刻検証、シフト確定と確定後の管理者編集、変更行だけの休憩再計算と本人集計、既存DB更新時の保持・ロールバックです。

```powershell
python -m pytest -q
```

今回の確定後編集への対応ではテストを追加・更新しましたが、テスト自体は実行していません。最新コードの成功件数・カバレッジを裏付ける実行記録も確認していないため、未確認の数値や「全件成功」の表示は記載していません。実行方法と対象ファイルは[テスト・セキュリティ](docs/security-and-testing.md)を参照してください。

パスワードのハッシュ保存、CSRF検証、ロール別認可、在籍・認証版のDB照合、ログイン試行制限、秘密鍵の環境変数管理を実装しています。これらは本番環境での安全性を保証するものではなく、公開運用前にはHTTPS・Cookie設定・公開用サーバー・依存関係・運用管理を改めて確認する必要があります。

## 10. 現在の開発状況と今後の予定

2026年10月20日時点の状況です。

- ローカルのSQLite版として、希望提出から確定・本人集計までの機能を実装しています。
- GitHubでソースコードを公開済みです。Webアプリのデプロイは未実施です。
- スクリーンショット・操作動画は未掲載で、架空データによる素材を準備する予定です。

今後は、SQLite版を維持しながら次の工程を進める方針です。

1. PostgreSQL対応：SQL・型・自動採番・制約・マイグレーション方法を見直す。
2. 本番向けの安全性確認：HTTPS、Cookie、秘密情報管理、権限、接続元IPとログイン制限、バックアップ・復元を検証する。
3. デプロイ：公開用の実行環境を整備し、Webアプリの公開後に動作を確認する。公開URL・QRコードの案内はその後に行う。

確定解除、管理者による希望代理入力、日跨ぎ・1日複数勤務、勤怠実績、正式な給与計算、時給改定履歴、CSV・PDF・メール、複数店舗は現行版の対象外です。機能を追加する際は要件を再整理します。希望勤務上限・扶養判定・必要人数管理等は、今後の追加予定にも含めていません。

秘密情報の扱いと公開後のチェックは[テスト・セキュリティ](docs/security-and-testing.md)、データと仕様の詳細は[システム設計書](system_design.md)を参照してください。
